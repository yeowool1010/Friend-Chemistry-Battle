# 창업 시뮬레이션 프로그램 정리

업종, 지역, 예산을 넣으면 창업 전·중·후를 계산하고, 공공데이터 오픈 API로 점포 수와 주민등록 인구를 붙인 뒤, 그 숫자로 안내 문장을 만드는 Next.js 앱이다. 계산된 조건으로 최대 5년짜리 가게 운영 게임도 이어서 할 수 있다.

패키지 이름은 `shop-sim`이고, 화면 제목은 **창업 시뮬레이션**이다. 저장소 폴더 이름 `Friend-Chemistry-Battle`은 이전 서비스 이름이며, 그 화면 코드는 아직 `src/app`에 남아 있다. 지금 상단 메뉴에 연결된 서비스는 창업 시뮬레이션이다.

## 화면

| 경로 | 화면 | 하는 일 |
| --- | --- | --- |
| `/` | 시뮬레이션 | 업종·지역·예산·평수·희망/절망을 고르고 한 번에 계산한다. |
| `/chat` | 대화모드 | 같은 계산을 보기 선택으로 단계마다 진행한다. |
| `/play` | 창업 게임 | 고른 조건으로 달을 넘기며 영업한다. 상단 메뉴에는 없고, 시뮬레이션이나 대화가 끝난 뒤 들어간다. |
| `/ask` | 자료 질문 | 창업 질문을 네 문장 이내 답으로 받는다. 상단 메뉴에는 없다. |

상단 메뉴는 `/`와 `/chat`만 연결한다. 공통 레이아웃은 `src/app/layout.tsx`, 메뉴는 `src/components/SiteHeader.tsx`다.

## 사용자가 거치는 흐름

1. 업종 대분류와 중분류, 시·구·행정동, 예산(만원), 평수를 고른다. 시뮬레이션에서는 지역을 “추천”으로 두거나 랜덤으로 돌릴 수 있다. 대화모드의 평수는 15평으로 고정된다.
2. 브라우저 안에서 자금 배분을 계산한다. 이 단계는 외부 API를 쓰지 않는다.
3. 서버 액션이 공공데이터 오픈 API 두 개를 동시에 호출한다. 하나는 같은 업종 점포 수, 다른 하나는 주민등록 인구다.
4. 조회된 숫자를 프롬프트에 넣어 생성 API가 창업 중 계획 JSON을 만든다. 이어서 창업결과 문장을 만든다.
5. 화면에 창업결과, 창업 전, 창업 중, 창업 후가 나온다. 점포는 행정동 막대 차트로 그린다.
6. “창업 시작하기”를 누르면 생성 API가 업종에 맞는 가게 문장과 상가 시세 JSON을 만들고, `sessionStorage`에 넣은 뒤 `/play`로 이동한다.
7. 게임은 2026년 11월부터 최대 60개월(5년) 동안 영업·재고·홍보·가격을 고른다. 이 루프는 로컬 계산이고 오픈 API를 다시 부르지 않는다.

시뮬레이션 결과는 `localStorage` 키 `shop-simulation-saves`에 최대 20개, 대화는 `shop-chat-saves`에 최대 20개 저장된다. 서버 데이터베이스는 쓰지 않는다.

## 오픈 API

현재 서비스가 부르는 공공데이터 오픈 API는 두 개다. 둘 다 공공데이터포털 서비스 키 `DATA_GO_KR_SERVICE_KEY`를 쿼리 파라미터 `serviceKey`로 붙인다. 키 읽기는 `src/lib/serverEnv.ts`의 `readServerEnv`이고, 요청이 들어온 뒤에 환경 변수를 읽는다. 키가 없거나 호출이 실패하면 해당 숫자만 비우고, 월세·인테리어 같은 로컬 계산은 그대로 보여 준다.

호출은 모두 서버에서 일어난다. `src/lib/enrich.ts`와 `src/lib/ask.ts`, `src/lib/shopVoice.ts`는 `"use server"` 서버 액션이라, 브라우저가 서비스 키를 받지 않는다.

### 어디서 호출되나

| 사용자 행동 | 함수 | 오픈 API |
| --- | --- | --- |
| 시뮬레이션에서 계산 실행 | `Simulator.run` → `enrichSimulation`, `loadAreaResidents` | 상가 점포, 주민등록 |
| 대화에서 행정동까지 고름 | `Conversation.showBefore` | 상가 점포, 주민등록 |
| 업종·지역·예산만 같고 희망/절망만 바꿈 | `draftOutcome`만 다시 호출 | 오픈 API는 다시 부르지 않음 |
| 창업 시작, 자료 질문, 안내 문장 | 생성 API | 오픈 API 아님. 아래 “생성 API” 참고 |

지역을 “추천”으로 두면 카탈로그에 있는 후보 구의 시군구 코드 목록으로 점포와 인구를 합산한다. 구를 직접 고르면 그 구 코드 하나만 넘긴다. 행정동을 고르면 인구는 그 동만, 점포는 구 전체를 받아 동 이름으로 센 뒤 고른 동을 표시한다.

### 1. 상가정보 — 행정동별 상가업소

- 파일: `src/lib/enrich.ts`의 `countStores`, `listDongNames`
- 주소: `https://apis.data.go.kr/B553077/api/open/sdsc2/storeListInDong`
- 제공 계열: 소상공인시장진흥공단 상가(상권)정보 오픈 API
- 용도: 고른 시군구·업종의 업소 목록에서 행정동 이름(`adongNm`)만 모아 동별 점포 수를 만든다.

요청 파라미터:

| 파라미터 | 값 |
| --- | --- |
| `serviceKey` | `DATA_GO_KR_SERVICE_KEY` |
| `type` | `json` |
| `divId` | `signguCd` (시군구 단위) |
| `key` | 시군구 코드 5자리. 예: 인천 남동구 `28200` |
| `indsLclsCd` | 업종 대분류. 예: 음식 `I2` |
| `indsMclsCd` | 업종 중분류. 예: 한식 `I201`. 있으면 붙인다. |
| `pageNo` | 1부터 |
| `numOfRows` | `1000` |

한 시군구당 최대 8페이지를 받는다. 한 페이지가 1000건 미만이거나 누적 건수가 `totalCount`에 닿으면 멈춘다. 8페이지를 채워도 총건수에 못 미치면 `partial: true`로 두고, 화면은 “일부 업소만 받아 순서가 달라질 수 있습니다”라고 표시한다. 타임아웃은 20초다.

응답에서 쓰는 필드:

- `header.resultCode`: `00`이면 성공, `03`이면 데이터 없음(0곳). 그 외이거나 HTTP 실패면 그 시군구 조회를 포기한다. 첫 페이지 실패는 전체를 비우고, 이후 페이지 실패는 받은 만큼만 남기고 부분 조회로 표시한다.
- `header.stdrYm`: 기준 연월. 차트 캡션의 “YYYY년 M월 기준”이 된다.
- `body.totalCount`: 시군구 전체 점포 수.
- `body.items[].adongNm`: 행정동 이름. 건수 집계에만 쓴다. 상호, 좌표, 주소는 저장하지 않는다.

여러 시군구(추천, 또는 고양 일산처럼 동구·서구를 묶은 후보)는 `Promise.all`로 동시에 받고, 동 이름을 공백 제거 키로 합친다. 로컬 지역 목록의 행정동은 점포가 0곳이어도 분포에 넣는다.

이 스냅샷은 `src/lib/competition.ts`에서 포화도로 바뀐다.

- 점포가 있는 행정동의 점포 수 중앙값을 기준으로 한다.
- 고른 행정동이 있으면 그 동 점포 수 / 중앙값. 없으면 가장 많은 동의 배율을 쓴다.
- 0.7배 이하는 한산, 2배 이상은 붐빔, 그 사이는 보통이다.
- 상위 8개 동의 “이름 N곳” 문자열이 이후 생성 프롬프트의 분포 문장이 된다.
- 매출 기준 점포 수는 선택 행정동에 점포가 1곳 이상이면 그 수, 없으면 시군구 합계다.

### 2. 행정안전부 주민등록 인구 및 세대현황

- 파일: `src/lib/resident.ts`
- 진입점: `enrich.ts`의 `loadAreaResidents` → `loadResidentPopulation`
- 주소: `https://apis.data.go.kr/1741000/stdgPpltnHhStus/selectStdgPpltnHhStus`
- 용도: 구 또는 행정동의 주민등록 인구(`totNmprCnt`)와 세대수(`hhCnt`)를 받는다.

요청 파라미터:

| 파라미터 | 값 |
| --- | --- |
| `serviceKey` | 상가정보와 같은 키 |
| `type` | `JSON` |
| `srchFrYm`, `srchToYm` | 같은 달. `YYYYMM` |
| `numOfRows` | `1000` |
| `pageNo` | 1부터, 최대 20페이지 |
| `stdgCd` | 조회 단위 코드 |
| `lv` | 단계. 아래 표 |

조회 달: 서울 시간 기준 직전 달, 그 달이 비면 두 달 전. 코드 주석대로 광주·전북 시군구 코드는 이 API가 받는 코드로 `src/data/regions.json`에 들어 있다.

`lv` 의미와 호출 순서:

| 상황 | `lv` | `stdgCd` | 하는 일 |
| --- | --- | --- | --- |
| 구 전체 | `6` | 시군구 5자리에 `00000`을 붙여 10자리 | 구 인구·세대 한 행 |
| 행정동, 1단계 | `3` | 동 코드 앞 5자리를 같은 방식으로 10자리 | 구 아래 법정동 목록 |
| 행정동, 2단계 | `4` | 법정동의 `stdgCd` | 법정동 아래 행정동의 `admmCd`별 인구·세대 |

행정동 조회는 법정동마다 `lv=4`를 치므로 호출이 많다. 동시에 3개만 돌리고(`mapPool`), 한 번 실패하면 400ms, 800ms, 1200ms, 1600ms 간격으로 최대 4번 다시 받는다. 주석은 초당 호출 제한과 일시 오류를 그 이유로 적는다. 응답에 `OpenAPI_ServiceResponse`가 있으면 정상 본문이 아닌 것으로 보고 재시도한다.

응답 판정:

- `Response.head.resultCode`가 `0`이면 성공, `3`이면 빈 결과, 그 외는 실패.
- 구 결과는 메모리 맵 `guCache`, 동 표는 `dongCache`에 둔다. 부분 조회(`partial`)인 동 표는 캐시하지 않는다.
- 세대당 인구는 `인구 / 세대`를 소수 둘째 자리로 반올림한 값이다.

화면의 “유동” 칸은 이 인구를 보여 준다. 계획용 카탈로그의 유동(많음/보통/한산)과는 별개다.

### 오픈 API 숫자가 계산에 쓰이는 방식

오픈 API는 월세, 보증금, 인테리어 금액을 바꾸지 않는다. 그 금액은 `src/lib/catalog.ts`와 `src/lib/simulate.ts`의 계획 기준이다.

오픈 API 숫자는 두 곳에 들어간다.

1. 화면의 경쟁 칸, 유동 칸, 행정동 점포 차트.
2. 생성 API 프롬프트. `enrich.ts`의 `openingPrompt`와 `outcomePrompt`가 “조회됨”이라고 표시한 인구, 세대, 시군구 점포, 선택 동 점포, 동별 분포를 넘긴다. 프롬프트는 이 값을 없다고 말하지 말라고 지시한다.

매출 구간의 기준식은 프롬프트와 `withKnownSales`에 같다.

- 점포당 배후 인구 = 주민등록 인구 / 매출 기준 점포 수
- 배후의 8%가 한 달에 한 번, 객단가 1만 5천 원으로 온다고 보면 기준 매출(만원) = 배후 인구 × 0.12
- 보수 0.7배, 여유 1.4배
- 모델이 기준 매출을 0으로 줬는데 인구와 점포가 모두 1 이상이면 서버가 이 식으로 다시 채운다.
- 인구 조회가 실패했거나 시군구 점포가 0곳이면 매출은 0으로 남긴다.

모델이 만든 매출이 있으면, 월세 계획 기준이 있는 구에 한해 남는 돈을 `매출 - 월세 - 인건비 - 매출×변동비율`로 다시 계산한다. 카탈로그에 없는 시군구는 월세 기준이 없어 남는 돈을 비운다. 화면 문구는 이 값이 카드 매출 통계가 아니라고 적는다.

## 생성 API

문장과 일부 JSON만 Gemini와 OpenAI가 만든다. 공공데이터 오픈 API와 키가 다르고, 숫자 원천도 다르다. 공통 함수는 `src/lib/completeJson.ts`의 `completeJson`이다.

순서:

1. `GEMINI_API_KEY`가 있으면 `gemini-3.1-flash-lite`, 이어서 `gemini-3-flash-preview`를 시도한다.
2. 용량 부족, 429, 5xx, 타임아웃, JSON 파싱 실패면 다음 모델로 넘긴다. 키 거부처럼 용량 문제가 아닌 오류면 거기서 멈춘다.
3. Gemini가 끝나면 `OPENAI_API_KEY`로 `https://api.openai.com/v1/responses`를 호출한다. 모델은 `OPENAI_MODEL`이고, 없으면 `gpt-6-astra`다.
4. 둘 다 실패하면 `null`이 돌아오고, 화면은 “정리하지 못했습니다”를 보여 준다. 게임은 로컬 기본 문장과 기본 시세로 시작한다.

Gemini 요청:

- `POST https://generativelanguage.googleapis.com/v1beta/models/{model}:generateContent`
- 헤더 `x-goog-api-key`
- `responseMimeType: application/json`, `responseSchema`로 JSON만 받는다.
- `thinkingBudget: 0`, 타임아웃 25초.

OpenAI 요청:

- `POST https://api.openai.com/v1/responses`
- 헤더 `Authorization: Bearer`
- Gemini 스키마를 JSON Schema로 바꿔 `text.format.type = json_schema`, `strict: true`로 받는다.

생성 API를 부르는 지점:

| 함수 | 파일 | 만드는 것 | 오픈 API 숫자를 넣는가 |
| --- | --- | --- | --- |
| `draftOpening` | `src/lib/enrich.ts` | 상권 문장, 준비·운영 문장, 인허가 주 수, 인테리어 비율, 집기, 계약 확인, 인허가, 성수기, 매출 3구간, 인건비, 변동비율 | 넣음 |
| `draftOutcome` | `src/lib/enrich.ts` | 희망편 또는 절망편 창업결과 6~8문장 | 넣음 |
| `askQuestion` | `src/lib/ask.ts` | `/ask` 답. 네 문장 이내. 오픈 API·공공데이터·다운로드 링크를 제안하지 말라고 지시함 | 넣지 않음. 질문 문장만 넘김 |
| `draftShopVoice` | `src/lib/shopVoice.ts` | 게임 상호, 상품명, 버튼, 영업시간, 7개 이벤트 문장 | 넣지 않음. 업종·지역·예산·평수만 넘김 |
| `draftShopMarket` | `src/lib/shopVoice.ts` | 매매/전세/월세와 월세·보증금·전세·매매가 | 넣지 않음. 앵커는 로컬 월세 |

`draftShopMarket`의 월세는 로컬 앵커의 0.5~2배, 보증금은 월세 5~20개월, 전세는 80~180개월, 매매는 150~400개월로 서버에서 한 번 더 자른다. 인테리어를 뺀 남은 예산으로 매매·전세를 낼 수 없으면 월세로 내린다. 이 시세는 오픈 API 실거래가 조회가 아니다.

희망편인데 예산이 보증금+운영비 3개월보다 작으면(월세 기준이 없으면 1,000만원 미만) 프롬프트가 “그 예산으로 가게를 여는 희망은 불가능하다”는 문장을 쓰게 한다. 대화모드의 창업결과는 항상 희망편 입력으로 요청하고, 예산이 부족하면 같은 분기를 탄다.

## 오픈 API 없이 하는 계산

`src/lib/simulate.ts`의 `simulate`는 입력만으로 결과를 만든다.

- 예산은 500만~10억 원(500~100,000만원), 평수는 5~80평으로 자른다.
- 인테리어는 예산의 35% (`INTERIOR_RATIO`).
- 보증금은 월세 × 10개월, 운영비는 월세 × 3개월.
- 남는 돈 = 예산 − 인테리어 − 보증금 − 운영비.

월세 계획 기준은 `src/lib/catalog.ts`의 `DISTRICTS` 12곳만 있다. 평당 월세에 평수를 곱한다.

| gangnam | 서울 강남구 | 11680 | 20 |
| mapo | 서울 마포구 | 11440 | 14 |

이 목록에 없는 시군구는 `planned: false`다. 월세·보증금·운영비·후보 지역이 비고, 화면은 “이 시군구는 월세 계획 기준이 없습니다”라고 보여 준다. 점포와 인구 오픈 API는 그 경우에도 호출한다.

“추천”은 이 12곳을 예산 적합, 유동, 업종 포화 점수로 정렬해 1위를 고른다. 포화 점수는 음식·수리개인·소매만 카탈로그에 있고, 나머지 대분류는 포화 점수를 더하지 않는다. 카탈로그 포화(한산/보통/붐빔)는 계획용 상수다. 오픈 API 점포가 도착하면 화면 경쟁 칸은 `judgeCompetition` 결과로 바뀐다.

업종 프로필(`PROFILES`)은 한식 `I201`, 비알코올 `I212`, 이용·미용 `S207`만 있다. 매출 기본 구간, 인건비, 변동비율, 인허가, 집기, 공사 주 수의 시드가 들어 있다. 생성 API가 계획을 만들면 화면의 주 수·매출·인허가는 그 JSON을 따른다.

업종 트리 전체는 `src/data/industries.json`이다. 대분류는 음식, 소매, 수리·개인, 과학·기술, 교육, 보건의료, 부동산, 숙박, 시설관리·임대, 예술·스포츠다. 코드는 상가업종 대·중분류 코드와 같아서 오픈 API의 `indsLclsCd`, `indsMclsCd`로 그대로 나간다.

행정동 목록은 `src/data/regions.json`이다. 시·구·행정동 이름과 코드가 로컬 파일이고, 지역 선택 자체는 API가 아니다. `dongsInSigngu`가 이 파일에서 동 이름을 꺼내 점포 0곳인 동까지 분포에 채운다.

## 창업 게임

`src/lib/play.ts`가 규칙을 갖고, `src/components/ShopGame.tsx`가 `/play`에 그린다. 설정은 `sessionStorage` 키 `shop-play-setup`이다. 직접 `/play`를 열면 설정이 없어 “가게가 없습니다”가 나오고 `/chat`으로 돌려보낸다.

시작 전에 `draftShopVoice`와 `draftShopMarket`을 동시에 호출한다. 음성(문장) 생성에 실패하면 `localShopVoice`가 업종 대분류에 맞춰 둔 기본 문장을 쓴다. 시세 생성에 실패하면 월세 10개월 보증금, 120개월 전세, 250개월 매매, 계약은 월세인 `fallbackMarket`을 쓴다.

한 달 행동:

- 영업: 가격(저·중·고)과 단골, 재고, 이벤트 문장으로 하루 매출을 누적한다.
- 재고 채우기, 홍보: 각각 비용이 나간다.
- 월세 계약이면 월세가 빠진다. 매매·전세는 시작 때 목돈을 이미 뺐다.
- 잔액이 무너지면 문을 닫고, 60개월을 채우면 “5년 · 계속 영업”으로 끝난다.

인구와 점포 수는 설정에 복사해 두지만, 달마다 오픈 API를 다시 부르지는 않는다.

## 저장소에 남아 있는 이전 서비스

`src/app/test`, `src/app/profile`, `src/app/result`, `src/app/waiting`, `src/app/b/[id]`, `src/app/c/[code]`는 제목이 “친구 케미 배틀”인 이전 화면이다. 상단 메뉴와 창업 시뮬레이션 흐름에서는 링크로 이어지지 않는다. `package.json`에도 그 화면이 기대하는 Supabase, PostHog 패키지가 없다.

그 코드가 외부 API를 부르는 방식은 지금 서비스와 다르다.

- `src/lib/ai/aiService.ts`는 `OPENAI_API_KEY`가 `sk-`로 시작할 때만 `src/lib/ai/openaiAiService.ts`를 고르고, 아니면 `src/lib/ai/geminiAiService.ts`를 고른다. `src/lib/ai/requestChemistryAnalysis.ts`가 이 경로로 케미 분석 문장을 요청한다.
- `src/lib/supabase/server.ts`는 Supabase에 배틀과 결과를 넣는다.
- `src/lib/kakaoShare.ts`는 `https://sharer.kakao.com/picker/link`로 초대 링크를 연다. 키는 `KAKAO_JAVASCRIPT_KEY`.
- `src/instrumentation-client.ts`와 `src/lib/analytics.ts`는 `NEXT_PUBLIC_POSTHOG_PROJECT_TOKEN`이 있을 때 PostHog로 이벤트를 보낸다.

창업 시뮬레이션의 오픈 API·생성 API 경로는 `completeJson`, `enrich`, `resident`이고, 케미 배틀 경로는 `aiService`다. 두 경로는 키 이름만 겹치고 호출 함수는 공유하지 않는다.

## README와 코드가 다른 점

루트 `README.md`는 “반경 500m 점포 수”라고 적고, “문장만 Gemini가 다듬는다”고 적는다. 현재 코드는 반경 검색을 하지 않고 시군구 행정동 업소 목록(`storeListInDong`)으로 동별 점포를 센다. 문장 생성은 Gemini 용량이 없으면 OpenAI로 넘어가고, 계획 JSON(주 수, 매출 구간, 인허가, 인테리어 비율)도 생성 API가 만든다. 월세와 자금 배분만 로컬 계획 기준이다.
